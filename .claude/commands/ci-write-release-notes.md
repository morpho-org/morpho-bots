# ci-write-release-notes

## Instructions

Analyze each release tag, compare it to the previous release, and update the GitHub release notes
with a comprehensive summary.

### Step 1: Parse Release Tags

The release tags are provided in the `RELEASE_TAGS` environment variable as a space-separated list.

Tag format: `{bot-name}-{version}` where version follows CalVer pattern `YYYY.MM.DD-N`

Example: `market-making-2026.08.04-1`

Loop through each tag and extract the bot name and version. Skip any tags that don't match the
expected pattern.

### Step 2: Analyze Each Bot

For each release tag:

1. **Find the previous release tag** for that bot:

   ```bash
   git tag -l "{bot}-*" --sort=-version:refname | head -5
   ```

2. **Compare the diff** between the newly-published tag and the previous one. Bots assemble their
   behavior from the shared `packages/*` workspace, so include it alongside the bot's own tree:

   ```bash
   git diff {previous-tag}...{new-tag} -- bots/{bot} packages
   ```

3. **Get commit messages** in the release range for context:

   ```bash
   git log {previous-tag}...{new-tag} --oneline -- bots/{bot} packages
   ```

4. **Extract PR numbers** from commit messages:

   ```bash
   # Get PR numbers from merge commits and PR references
   git log {previous-tag}...{new-tag} --oneline -- bots/{bot} packages | \
     grep -oE '#[0-9]+' | \
     sort -u
   ```

   This captures:
   - Merge commit patterns: `Merge pull request #123`
   - PR references in commit messages: `feat: add feature (#123)`
   - Ensures no duplicates with `sort -u`

   Store these PR numbers for use in:
   - Inline changelog references (match commits to PRs)
   - The "Merged Pull Requests" section at the bottom

5. **Analyze the changes** by examining:
   - Commit messages: understand the intent and scope
   - Code diff: identify what actually changed
   - Package.json: check for dependency updates or version bumps
   - Breaking changes: look for major refactors or API changes

6. **Write a comprehensive summary** with:
   - **Overview**: 1-2 sentences describing the main purpose/theme of this release
   - **Changelog**: 3-5 bullet points covering new features, bug fixes, improvements, breaking
     changes, or significant dependency updates
     - Include PR numbers inline where applicable (e.g., "Adds feature X (#123)")
     - Match commits to their PR numbers from the extracted list
     - Use format: `{description} (#{pr_number})`
   - **Technical Notes** (if relevant): major configuration changes or rewrites to be aware of

   **Matching commits to PRs:**
   - Look at the commit message for PR references
   - If a commit mentions `(#123)` or is a merge commit for that PR, use that number
   - If multiple commits relate to the same PR, mention the PR once in the summary
   - If a commit has no clear PR association, omit the PR reference for that item

### Step 3: Post Release Notes

Use `gh release edit` to update each release with the generated notes:

**Building the Merged Pull Requests section:**

- Use the deduplicated list of PR numbers from the extraction step
- Format each PR as `- #{number}` (GitHub will auto-link these)
- Sort PRs numerically in ascending order
- If no PRs were found, omit this section entirely

```bash
gh release edit "${RELEASE_TAG}" --notes "$(cat <<'EOF'
## Overview

{1-2 sentence summary}

## Changelog

- Adds feature X with improved performance (#456)
- Fixes critical bug in component Y (#789)
- Updates dependency Z to v2.0 (#123)

## Technical Notes

{A few words or bullet points if relevant}

## Merged Pull Requests

- #123
- #456
- #789

---

*Generated by Claude*
EOF
)"
```

### Guidelines

- **Be specific**: Mention actual features, components, or file names when relevant
- **Focus on impact**: Explain what changed and why it matters to users/developers
- **Skip noise**: Ignore pure refactors, linting, or formatting unless they affect behavior
- **Use active voice**: "Adds feature X", "Fixes bug Y", "Updates dependency Z"
- **Group related changes**: Combine similar fixes or features into single bullet points
- **Prioritize user-facing changes**: Features and bug fixes come before internal improvements
- **Include PR references**: Add PR numbers inline with changelog items when applicable (e.g., "Adds
  feature X (#123)")
- **List all PRs**: Include a "Merged Pull Requests" section at the bottom with all unique PRs from
  the release
- **Avoid accidental tagging**: Format `@something` as code to avoid listing @something as
  contributor

### Error Handling

- **No previous tag**: Note it's an initial release in the overview
- **Empty diff**: Mention this is a configuration/dependency update
- **Invalid tag format**: Skip the tag and continue with others

Process all releases in the list independently. Partial information is better than no information.
